AUTH CHANGE – REMOVE EMAIL/CLERK LOGIN AND USE LOCAL USERNAME + PASSWORD LOGIN

Replace Clerk/email login with a local username/password authentication system.

Important:
- No email login required.
- Login should use username + password only.
- Admin must be able to create and manage users.
- Keep existing roles and permissions.
- Keep Admin / Manager / Staff roles.
- Do not remove the permission system.
- Do not break existing protected pages.
- Prepare this for future desktop app usage.

1. Remove Clerk Dependency

Remove Clerk authentication from:
- Frontend
- Backend
- Protected routes
- API middleware
- Login/signup pages

Replace with local auth using PostgreSQL.

2. Users Table

Update users table to support:

- id
- username, unique
- passwordHash
- fullName
- role: Admin / Manager / Staff
- status: Active / Inactive / Archived
- permissions JSON/columns
- lastLoginAt
- createdAt
- updatedAt
- deletedAt

Do not store plain passwords.

Use bcrypt or argon2 for password hashing.

3. Login Page

Create simple login page:

Fields:
- Username
- Password

Buttons:
- Login

No sign up button for staff.

Only Admin can create users from Settings or Staff permissions page.

4. Auth Backend

Create endpoints:

POST /api/auth/login
- Accept username + password
- Verify password hash
- Reject inactive/archived/deleted users
- Return session/JWT token and user info

POST /api/auth/logout
- Clear session/token

GET /api/auth/me
- Return current logged-in user, role, permissions

POST /api/auth/change-password
- Current password
- New password
- Confirm password

5. Session System

Use JWT or secure HTTP-only cookie.

Requirements:
- Token/session expires safely
- Protected API routes require valid login
- Frontend stores auth safely
- Logout clears auth
- Refresh page should keep user logged in if session is still valid

6. First Admin Setup

If no users exist:
- Show setup screen to create first Admin account

Fields:
- Full name
- Username
- Password
- Confirm password

After first admin is created:
- Disable public signup forever

7. User Management

In Settings or Staff page, add User Management section.

Admin can:
- Create user
- Edit user
- Set username
- Set full name
- Set role
- Set permissions
- Reset password
- Activate/deactivate user
- Archive user

Manager can only manage users if permission allows.

Staff cannot manage users.

8. Password Rules

Add validation:
- Minimum 6 characters
- Confirm password must match
- Username must be unique
- Username cannot be empty
- Password reset requires Admin permission

9. Permissions Integration

All existing permission checks must continue working.

Backend must enforce:
- viewAccounting
- viewCost
- viewProfit
- manageMembers
- manageInventory
- managePayroll
- manageSettings
- manageStaff
- managePlans

Do not rely only on frontend hiding.

10. Activity Logs

Log:
- User login
- User logout
- Failed login attempt
- User created
- User edited
- User deactivated
- User archived
- Password changed
- Password reset by admin

11. Migration

Since Clerk IDs were used before:
- Add migration path to convert existing users into local users.
- For existing users without password, Admin should reset/create passwords.
- Do not delete existing user permissions.
- Keep activity logs linked where possible.

12. UI Requirements

- Clean login page
- No email required
- No external auth branding
- Settings/User Management page clean and simple
- Toast success/error messages
- Loading states
- EN / FR / AR translations
- Arabic RTL still works

13. Final Testing

Test:
- First admin setup
- Admin login
- Manager login
- Staff login
- Wrong password rejected
- Inactive user rejected
- Archived user rejected
- User permissions still restrict pages
- Backend APIs reject unauthorized access
- Password reset works
- Logout works
- Refresh keeps session if valid

Stop after local auth is complete and return a checklist.
